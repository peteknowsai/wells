Cold-boot substrate

Status: Accepted — both teams agreed 2026-06-17 · Date: 2026-06-17 · From: wells team · To: wells + cells

This proposal records a decision reached jointly by the wells and cells teams on 2026-06-17, kicked off by a cells question about Apple's WWDC 2026 Containerization release. It supersedes the warm-pool model described in cells-pool-builder-primitives.md and state-tiers.md for the pool case only. Live-cell hibernation is unchanged.

TL;DR

  • The egg pool exists for one reason: hide birth latency. Measured cold-boot of a lean well to ssh-ready is ~3.5s; cells's birth is a ~95s mother-ritual. 3.5s into 95s is noise — so a pool of cold eggs buys nothing. "Cold eggs" and "no pool" are the same thing.
  • Decision: delete the egg pool, birth cells cold on demand, and stop sealing pool eggs — seal drops from once-per-egg to once-per-cell. cells
  • Keep RAM-hibernation only where it earns its keep — pausing live cells that have work in memory. wells
  • Lean the base image: fold safe daemon cuts into ubuntu-25.10-base — measured ~18% idle RAM/cell (263→216 MB), zero behavior change, DNS intact. wells
  • Keep /seal as the per-cell birth warming step — forks are born hibernate-illegal (cidata still mounted), so seal makes each cold cell hibernate-legal. Call volume drops from per-egg to per-cell, not to zero. wells
  • Don't switch engines to Apple Containerization — it has no RAM save/restore, which is exactly the hibernation we refuse to lose.

In plain English

What this changes, without the jargon

Today, to make a new agent fast, we keep a shelf of pre-built virtual machines that have been switched on, fully set up, then frozen mid-run — like a car left idling in the driveway. Grabbing one is instant. But freezing and un-freezing a running machine is fiddly, and it's been the source of our nastiest bugs (the clock jumping, the network going dead on wake).

It turns out we don't need the idling cars. Actually making a new agent already takes about a minute and a half of setup. Booting a machine from cold takes about three and a half seconds. Three and a half seconds on top of ninety-five is nothing — so the frozen shelf saves us almost no time while costing us a pile of fragile machinery.

So we're throwing away the shelf. New agents will just boot a fresh machine on demand. We keep the freezing trick for one case where it genuinely pays off: pausing an agent that's already doing work, so it wakes up exactly where it left off.

While we were in there, we also found the standard Linux image was running background junk no agent uses — chiefly an app-store updater (snapd) running with nothing to update. Cutting it gives every agent back about 18% of its idle memory, which lets us pack more agents onto the same hardware.

§1 — The core insight

The egg pool (warm, pre-sealed VMs waiting to be claimed) exists to hide one cost: the time between "we need an agent" and "the agent is reachable." That is its only job. Everything the pool drags along — the refill loop, eviction logic, reconcilePool(), and per-egg sealing — is overhead in service of that one latency win. (Sealing itself doesn't vanish: it survives as a once-per-cell step, since every cold cell must be made hibernate-legal — see §2.)

The latency win turns out to be negligible. Measured on this host:

PathTimeNotes
Hibernate-wake (warm egg claim)~0.55 sToday's pool path
Cold start → ssh-ready (lean well)~3.5 sProposed birth path
cells birth (mother-ritual, end-to-end)~95 sThe cost that actually dominates

The pool saves ~3 s on a ~95 s operation: about 3%. And the moment an egg is cold (powered off) rather than frozen, claiming it means booting it — which is identical work to creating a fresh well from scratch. A pool of cold eggs is therefore indistinguishable from no pool at all.

In plain English: the only thing the pre-built shelf buys is speed, and the speed it buys is a rounding error next to the minute-and-a-half of real setup. Not worth the machinery.

§2 — Architecture & ownership

The change is a clean subtraction on the cells side and a small, optional improvement on the wells side. The substrate primitives cells leans on — create, start, stop, and live-cell hibernate/wake — are unchanged.

Cells owns

  • Delete the pool: pool.json, refill loop, eviction, reconcilePool().
  • Rewire birth: fork a fresh well from the pre-provisioned cell-base image → light identity imprint → mother configures.
  • Seal once per cell at birth (down from once per pool-egg) — birth's ensureHibernateReady → /seal makes the cold cell hibernate-legal.
  • Decommission the existing stopped pool eggs.

Wells owns

  • Lean ubuntu-25.10-base — fold in the safe daemon cuts (§3).
  • Keep primitives unchanged: create / start / stop.
  • Keep live-cell hibernate/wake exactly as-is.
  • Keep /seal as the per-cell warming primitive (halt → disk-only restart drops cidata → hibernate_ready=true). Not retired — forks are born hibernate-illegal.

How birth works without the pool cells

Birth does not re-install anything. The heavy provisioning — DNA, all four harness binaries (pi/codex/hermes + claude from the base), node-gyp, pi patches, env shim — is baked once into a reusable cell-base image via cells bake, re-run only when the DNA or toolchain materially changes. Each birth then forks a fresh well from that image — an APFS clonefile, sub-millisecond regardless of image size — and does only a light identity imprint before handing off to mother. So "provision at birth" is clone + imprint, not re-install: the ~3.5s cold-boot figure holds precisely because the install cost was already paid at bake time. (This replaces the pool's per-egg bake; the same provisioning recipe now feeds one image instead of N hibernated eggs.)

In plain English: we keep one fully-built master copy and stamp out fresh agents from it. Stamping is instant — we don't redo the build each time.

What stays: live-cell hibernation

Hibernation is not going away — only egg-sealing is. Pausing a live cell (one with a warm in-memory session) and resuming it with memory intact is high-value: a cold boot would force the harness to re-spawn and replay a potentially large session JSONL before the cell is useful again. That case keeps hibernate/wake.

The seal bug class shrinks but does not vanish. The seal-halt mechanics (e.g. the two-stage halt in 99c5110) still run — once per cell at birth instead of once per pool-egg-refill, a large reduction in volume but the same code path. The wake-time bugs (clock-step, TCP black-hole on wake) are RAM-restore artifacts; they now matter only for live-cell wake, where the value of a warm resume justifies the fight.

Verified 2026-06-17: forks are born hibernate-illegal

A well forked from an image (POST /v1/wells {from_image}) comes up hibernate_ready=false with the CIDATA disk still mounted; POST /hibernate refuses with 409 well_not_hibernate_ready. welld writes defaultRuntime() (hibernate_ready=false) on every create and re-attaches cidata for SSH/firstboot — so the image-save's clean shutdown is not enough to make a fork hibernate-legal. /seal's halt + disk-only restart (dropping cidata) is required once per cell. This is why the pool→cold-birth move reduces seal volume rather than eliminating it.

In plain English: we stop freezing empty machines (the fragile, low-value case) and keep freezing busy ones (the sturdy-enough, high-value case).

§3 — Lean base image wells verified

Independent of the pool decision, the stock Ubuntu image runs daemons no agent VM needs. Inspection of a fresh egg found snapd — the single largest process — running with zero snaps installed. The safe cut set, verified on a real reboot:

# in ubuntu-25.10-base
apt-get purge -y snapd networkd-dispatcher rsyslog haveged
apt-mark hold snapd
apt-get autoremove --purge -y && apt-get clean
systemctl set-default multi-user.target      # was graphical.target (no desktop installed — cosmetic)
systemctl disable getty@tty1.service         # headless; reached over SSH
rm -rf /snap /var/snap /var/lib/snapd /root/snap
# KEEP systemd-resolved — load-bearing (see DNS note)
MetricStockLeanΔ
Idle RAM used263 MB216 MB−47 MB (~18%)
Running services1710−7

Boot → ssh-ready (external)~3.5 s~3.5 s— (network-bound)

Verification on the lean variant: systemd-resolved active, resolv.conf → dynamic stub, getent hosts github.com OK, outbound HTTPS 200, apt-get update OK. A candidate image cell-base-lean (5.6 GB) was built and verified and remains in the wells image registry for cells to test against (throwaway wells were destroyed). The real home for these cuts, though, is ubuntu-25.10-base so every well inherits them on next pull — cells provisioning then layers only cells-specific things on top.

DNS: keep systemd-resolved

A static resolv.conf was tried to reclaim resolved's ~13 MB and rejected. The host DNS forwarder runs on 192.168.64.1:5353, and resolv.conf cannot express a port — so a static config silently bypasses the host's split-horizon DNS (*.cells.md, cell-to-cell names) and goes stale if the network shifts. Robustness over ~2%. Dynamic DNS stays.

§4 — Explicitly not doing (YAGNI)

TemptingWhy not
Switch engine to Apple Containerization (WWDC 2026, v1.0 June 9)Its "stop" is a clean shutdown and "start" is a cold boot — no RAM save/restore. That's exactly the live-cell hibernation we refuse to lose. Model mismatch, not a version wait.
Chase Apple's sub-second boot (mine vminitd / their kernel config)Our kernel already boots in ~260 ms. The cost is systemd userspace, and the residual ~3.5s to ssh-ready is network bring-up, not daemons. vminitd is a container init (userspace comes from the OCI image); we run a real distro, so it's not a drop-in. Not worth a custom-init rearchitecture when ~3.5s is already noise.
Keep a small warm pool "just in case"Reintroduces the entire machinery to save ~3s on a ~95s op. No.
Per-cell customization at birthA real capability the cold model unlocks (base image + light per-cell layer, container-style) — but not built now. Noted as future, not scope.

§5 — Migration

  • cells Delete the pool; rewire birth to fork from the pre-provisioned cell-base → imprint → mother-configure; bake cell-base via cells bake (refresh on DNA/toolchain change). (in flight)
  • cells Seal once per cell at birth (down from per-egg); decommission existing stopped pool eggs; ping wells when the migration lands.
  • wells Rebake ubuntu-25.10-base with the §3 cuts. No rush — cells inherits on next base pull.
  • wells Keep /seal as the permanent per-cell warming primitive. (Original "retire seal" goal dropped: forks are born hibernate_ready=false with cidata mounted, verified — seal is what makes each cold cell hibernate-legal.)

No coordinated bounce required. The two tracks are independent: the base rebake and the pool teardown don't block each other, and /seal remains a permanent per-cell primitive (no retirement step).

§6 — Risks & open questions

RiskAssessment
Birth now depends on a live boot every time (vs. a pre-baked claim)Low. Cold boot proved reliable across repeated test cycles. Failure modes are standard and retryable (boot fail, slow network) — not the freeze/thaw gremlins. And birth is dominated by the ~95s ritual regardless.
If birth latency ever does become a concernThe lever is the ~95s mother-ritual (cells's domain), not the ~3.5s substrate boot. Optimize there, not here.
Lean cuts break something subtle in a future provisioning stepCuts are generic Ubuntu-server cruft (app-store updater, network-event dispatcher, redundant syslog, entropy daemon). Verified green for DNS/outbound/apt. If a future need appears, re-add the specific package in provisioning.

Appendix — measurement provenance

All numbers measured 2026-06-17 on the wells host against the live cell-base image, via throwaway wells created and destroyed during the session:

  • Cold boot: create-from-image → ssh-ready ~4.8s (first boot, with cidata); stop → cold start → ssh-ready ~3.5s (claim-equivalent path).
  • Guest boot breakdown: systemd-analyze = ~260 ms kernel + ~2.8–3.5 s userspace.
  • RAM: idle free -m "used" after 8s settle — stock 263 MB, lean 216 MB. Top stock consumer: snapd 37 MB (with snap list empty).
  • ~95 s mother-ritual birth: cells team figure.
  • ~0.55 s hibernate-wake: existing wells pool figure.
